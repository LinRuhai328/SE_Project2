> 提交版以 `实验报告.pdf` 为准，本文件是可编辑的文字源；图中的内容以 `UML/` 下的 `.puml` 源码为准。

## 一、项目说明与主要功能

实验一交完之后，需求文档里留了一批“待确认”。真正卡住设计的只有三条：第三个角色是谁、个人账本要不要审核、结算之后还能不能改。这三条不定，类图画不出来，所以先定下来再谈结构。

项目没换，还是多人共享记账。场景是家庭、室友这种三五个人一起花钱：一个人记一笔，另一个人看过才算数，月底把这一期封起来。系统只管记账和统计，不碰真实支付，也不读银行和支付宝的账单接口——那些权限拿不到，截图导入只是补录手段。

### 1.1 功能模块划分

| 模块 | 主要功能 | 对应实验一需求 |
|---|---|---|
| 账号与账本 | 注册登录、会话管理、创建个人/共享账本、归档与恢复 | REQ-001、004、031、033 |
| 成员与权限 | 邀请与接受、角色分配、所有权移交、退出与再邀请 | REQ-002、003、004 |
| 记录与状态 | 新增、提交、审核、驳回、撤回、作废、更正与版本保留 | REQ-005—010 |
| 查询与统计 | 按类别/成员/日期/金额组合查询、分类与成员统计 | REQ-015—018 |
| 预算与结算 | 月度预算、超支提示、按月结算、锁月、重开与快照版本 | REQ-019、020、032 |
| 导入与通知 | 截图识别候选、去重与人工确认、站内通知与补发 | REQ-011、022—024 |
| 审计 | 操作日志、前后版本、原因记录、查询权限 | REQ-021、035 |

模块之间是有先后的：账本和账号是地基，成员关系长在账本上，记录依赖成员关系做权限判断，统计和结算只读有效记录与结算快照。写路径必须共用一套状态机，否则会出现页面能点、服务端拒绝的情况。

## 二、软件架构与 UML 建模

三类图各至少一种，类图必画。实际给了六张 UML 图加一张界面流转图：类图、组件图（结构性），用例图、活动图、状态图（行为性），时序图、界面流转图（交互性）。术语与实验一的需求文本保持一致。

- **2.1 类图**：四个包。成员关系从账本字段改成独立实体 Membership；结算结果冻结为 SettlementSnapshot；状态改成枚举。
- **2.2 用例图**：三类角色的边界。标注两条硬约束：更正不得自审、待审核阻断结算。
- **2.3 状态图**：六个状态与全部转换，每条箭头标触发条件与执行人。三处易错点：个人账本不走待审核、更正不覆盖原值、作废只换状态不删数据。
- **2.4 活动图**：把状态图放进一次完整操作，重点是字段校验、操作标识幂等、审核时的状态比对。
- **2.5 时序图**：提交与审核链路。幂等与冲突在服务端处理；审计落库先于通知发送。
- **2.6 组件图**：表现层、应用服务层、领域层、基础设施层。状态机、权限判定、校验单独成组件，服务层不得绕过。
- **2.7 模块交互与设计取舍**：写路径统一入口，读路径只读快照，外围能力可降级。
- **2.8 需求覆盖矩阵**：35 条需求按九组映射到图元素与界面编号。

## 三、界面设计

八个主页面加四张状态页。前八张是正常流程，后四张是会出问题的地方。统一两条规则：写操作按钮放行尾或右侧；状态用色块标签，颜色与活动图六种状态对应。

## 四、大模型辅助设计的过程记录

工具：OpenAI Codex 命令行会话，模型 gpt-5-codex（与实验一相同）。记四次成功使用与一次失败尝试，每次写场景、要求、输出、判断、优缺点、修改结果。

- 4.1 类图初稿：模型把角色写成账本字段，补 Membership 与快照；优点快，缺点是按最简模型建模。
- 4.2 活动图与状态机：模型把退回画成直接改金额，补更正三步与幂等；优点主线准，缺点异常分支为零。
- 4.3 界面结构：首页七个指标删到四个，批量通过加自审限制；优点结构规整，缺点不懂指标取舍。
- 4.4 PlantUML 语法：包与注释重叠，改 skinparam；优点可验证，缺点只修指出的一处。
- 4.5 一次失败的尝试：直接让它出图，改不动，退回 PlantUML 源码。
- 4.6 小结：模型会铺开会收；列出清单、铺流程、校语法三类可稳定采用，业务判断必须自己做。关于“能否让人只做校对”，答案是部分可行。

## 五、版本管理

提交前缀区分类型：feat 加图或页面，fix 修设计里的错，refactor 改结构，style 调视觉，docs 动报告。模型给初稿的提交写明“（模型生成）”。

两处修改可以直接对比：

```
git show 4c24529:UML/UML类图.puml      初版（缺成员实体与快照）
git show e181cb1:UML/UML类图.puml      改完的版本
git diff 4c24529 e181cb1 -- UML/       两次提交的实际差异
git log --stat -- UML/                  各图的演化与改动量
```

仓库没有删过提交，也没有改过历史；图和报告在同一条线上，任意中间版本都能检出。六个 ADR 写在 `设计决策记录.md`。

## 六、小结

改动最大的三处是成员关系、更正、结算快照。都不是画图问题：成员关系是“人能走、历史要留”，更正是“改过的账不能悄悄覆盖”，结算快照是“封存的账不能再动”。

四张图和八个界面够用了。类图里的类和接口实验三直接照着落代码；活动图里的三个判断点会变成服务层的三段校验。实现时如果发现设计有问题，按老师说的在实验三里说明，不回头改这份文档。
