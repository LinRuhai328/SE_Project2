# 需求约束摘要

从实验一的需求文档里摘出与设计直接相关的约束，画图前先对一遍，避免设计跑偏。

## 三条待确认，已定

1. **第三类角色**：实验一写的是“所有者 / 管理员 / 普通成员”，但没写清楚管理员能不能删账本。定了：不能，归档与删除只有所有者能做。
2. **个人账本要不要审核**：定了不审核。个人账本自己记自己看，提交即生效；共享账本必须另一人审核。
3. **结算之后能不能改**：不能直接改。要改必须先重开账期，由所有者填原因，旧快照保留为历史版本。

## 硬约束

| 约束 | 来源 | 设计上的落点 |
|---|---|---|
| 金额两位小数，不做四舍五入 | REQ-006 | 校验层直接拒绝，不静默修正 |
| 发生日期不能晚于今天 | REQ-006 | 表单与接口都校验 |
| 已提交的记录不能直接改 | REQ-009 | 状态图里“更正”走二次审核 |
| 禁止审核自己提交的记录 | REQ-008 | 权限判定里加提交人比对 |
| 待审核记录阻断结算 | REQ-019 | 结算前置校验 |
| 作废只换状态，不删数据 | REQ-010 | 审计与统计口径分开 |
| 账期锁定后只能查看 | REQ-020 | 所有写操作先查锁 |

## 模块边界

七个模块：账号与账本、成员与权限、记录与状态、查询与统计、预算与结算、导入与通知、审计。

写路径（新增、审核、作废、更正、结算）必须共用一套状态机与权限判定；读路径（统计、结算）只读有效记录与结算快照。这条是后面所有图的前提。
